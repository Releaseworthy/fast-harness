# D68: Background shell jobs

Owner, 2026-11-13: phase 31 "background shell jobs" (docs/architecture-plan.md finding A5). This is the core part; the TUI and GUI views are a second chunk. Before it, `shell` waited for the end and killed the process tree at the end, on timeout and on cancel, and its description said "do not start background servers here".

## Start: an argument of `shell`, not a new tool

`shell` takes `background: true`. Options were a flag on `shell` or a separate `job_start` tool. The flag wins because a start is the same call with the same risk: the approval gate (D64) asks for it as `shell` (effect `Run`), the `allow.commands` prefixes and the fail-closed command matching apply unchanged, PreToolUse hooks matching `shell` see it, the view's `shell` row and `-p` refusal text need nothing new, and one spec fewer stays in the deferred list. The approval summary says `run in the background: <command>` and the session grant key is `background: <command>`, so allowing a command once for this session in the foreground does not also allow starting it in the background (the `allow` list still covers both: an allowed command may run either way).

A background call returns at once with `started job-<n> in the background`, the output printed within a grace of 1 s (or until it ends, if sooner) and the state line. `timeout_ms` does not apply: a job runs until it ends, `job_kill` stops it or its session closes. The description now points to background jobs.

## The job tools (deferred behind `find_tools`, D30)

- `job_output {id, wait_ms?, until?}`: the new output since the last read, then `[job-1 is running: ...]`, or `[job-1 ended]` / `[job-1 was killed with its process tree]` followed by `[exit code: N]`. `wait_ms` (0 to 120000, default 0) waits for new output, or with `until: "end"` for the end. Effect `Read`, like `agent_output` (D54): it starts and stops nothing; it only moves the job's read cursor, so two reads of one job in one step each get a disjoint part. Its result budget keeps head and tail like `shell`.
- `job_kill {id}`: kills the whole process tree (`platform::ProcessGroup::kill`, the Job Object on Windows) and waits up to 5 s for the exit. Effect `Run`, so with `approvals: ask` it asks unless `allow.tools` names it. It is not exempt like `agent_stop`: the owner rule for this phase is approvals like `shell`.
- `job_list {}`: one row per job (`job-1  running  120 bytes  <command>`). Effect `Read`.
- Every tool but `find_tools` stays deferred: the job tools are added to `tools::builtin()` after `glob`, so `find_tools`' description lists them and the first request still carries only `find_tools` loaded (on Claude the rest with `defer_loading`).

## Runtime (`tools/jobs.rs`, `tools/job_buffer.rs`, `tools/job_tools.rs`)

- **Owner.** `ToolSession::jobs()` (`Arc<Jobs>`), so a job belongs to the conversation's session. `service::Session` holds the same `Arc` (taken from the conversation at open); a conversation reopened after a panic gets it back (`ToolSession::share_jobs`, `service/turn.rs` `reopen`), so a crash in a turn does not kill the session's servers.
- **No polling.** One thread per pipe blocks on `read` and appends to the buffer; one thread blocks on `Child::wait`. Readers wait on a condition variable. The only timed slice is a 200 ms backstop while a `job_output` wait also watches the call's cancel flag (an `AtomicBool` cannot wake a condition variable), as the approval gate's 500 ms backstop (D64).
- **End.** When the shell exits, the waiter kills what is left of its group (`ProcessGroup::kill_rest`: the Job Object on Windows; nothing on the fallback, where the reaped pid may already be another process) so the pipes close; a job has ended once it exited and both pipes reached their end.
- **Caps.** At most `MAX_RUNNING` = 8 running jobs per session (a 9th start is an error naming `job_kill`); at most 32 jobs listed (the oldest ended ones go). Output per job: the newest `RING` = 64 KiB in memory, plus a log file `<session>.out/job-<n>-<unix ms>.log` holding the first `LOG_CAP` = 16 MiB (a stream appended in place, not a settings file, so not through `store`). A read that fell behind the ring says how many bytes it skipped and names the log.
- **Session end.** `Service::close` calls `Jobs::kill_all` (after the turn stopped and the children went, D67) and waits up to 5 s for the exits. The last `Arc<Jobs>` to drop kills every running job (`-p`, a subagent's own conversation, a front end that never closes). At process exit the Windows Job Object handles close and `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` kills each tree; the fallback platform has no process trees and its leftovers may outlive the process.
- **Subagents.** A child conversation has its own `ToolSession`, so its jobs are its own and die when the child's conversation drops.

## View API (for the second chunk)

`Session::jobs() -> Arc<Jobs>`; `Jobs::list() -> Vec<JobInfo>` (`id`, `command`, `state`: `JobState::{Running, Exited, Killed}`, `exit_code`, `started`, `bytes`, `log`), `Jobs::revision() -> u64` (one more per start, end or kill) and `Jobs::wait_change(since, timeout) -> u64`, which blocks on a condition variable: a view's worker thread waits there and posts to its UI thread. No `AgentEvent` variant: jobs outlive turns, and a turn's sink is gone between turns. No trace record: the tool calls and results are traced as any call, and a replay needs nothing else (D61); no format change.

## Views

The second chunk: the TUI and the GUI show the shown session's jobs.

- **Model (core `view/jobs.rs`).** `rows(&[JobInfo]) -> Vec<JobRow>`: per job its id, the command shortened (first non-empty line, spaces collapsed, cut at 40 characters with `…`), a word (`running`, `exited N`, `exited`, `killed`) and a `Mark` (`Running`, `Exited` for code 0 or none, `Failed` for another code, `Killed`). Both front ends draw these rows.
- **One worker per front end, no timer.** `Watch::start` spawns `fast-harness-jobs`, which blocks in `Jobs::wait_change_or_stop(since, stop)` (new: `wait_change` without a timeout plus a stop flag) and posts `Jobs::list()` after each start, end or kill. `Jobs::wake` takes the revision lock and notifies, so dropping the `Watch` ends its worker at once; a finite `wait_change` timeout would have been a timer, or left a stale worker parked on the previous session. `Follow` (UI thread) holds the one `Watch`: `target(jobs)` keeps it for the same `Jobs` (`Arc::ptr_eq`), else replaces it with the next generation, reading the revision before the list it returns for the immediate draw. `arrived(generation, list)` drops a list of an earlier generation; `target(None)` stops the worker and shows nothing.
- **TUI (`tui/jobs.rs`).** `shown()` (start and every switch) re-targets; posts arrive as `Msg::Jobs(generation, list)`. One line above the input, only while the session has jobs: `jobs  ○ job-1 ping -t localhost running  ✓ job-2 cargo build exited 0`, marks `pending`, `ok`, `error`, `not_run` of the icon set (one cell wide) in the accent, success, error and warning roles, each with its word. `/kill <job-id>` calls `Jobs::kill` (the kill of `job_kill`) on a thread, since it waits up to 5 s; the user typed it, so the approval gate does not ask.
- **GUI (`jobs_view.rs`, `ui/jobs.slint`).** `show_run` (every switch) and `launch` (the first turn opens the session in the service) re-target; posts come back through `slint::invoke_from_event_loop`, whose error ends the worker; `run` stops the watch when the event loop returns. `JobsRow` sits between the queue chips and the approval prompt while `jobs` is not empty: per job a chip with a mark (`terminal`, `check`, `error`, `circle-slash`) and the word in a theme role, the id, the elided command, and Stop (`debug-stop`) while it runs, calling `kill-job(id)`, the same kill on a thread. New `MainWindow` items `jobs: [JobChip]` and `kill-job(string)` (`docs/ui-contract.md`). Replaced by a pill and a popover with the job's output in D72. A session without a turn in this window has no service session, so no jobs and no worker.
- **Tests.** Core `view/jobs_tests.rs` (words and marks, shortening, a change posts and stop ends the worker, a switch re-targets and drops a stale list); TUI `jobs_tests.rs` (buffer render with running, exited and failed jobs and their roles, no line without jobs, the worker feeds the line, a stale list is dropped, `/kill` ends the job); GUI `jobs_view_tests.rs` (row model, a software window draws the strip only with jobs).
- **Cost.** Idle numbers in `docs/perf.md` "Phase 31 views": private working set and idle CPU unchanged within run-to-run noise.

## Tests

`tests/shell_jobs.rs`: a job that prints and keeps running returns its id at once; reads return only new output; `until: "end"` gives the output and exit code 3; a kill ends a grandchild (`Start-Process ping`, Windows); `Service::close` kills a session's job and bumps the revision; the running cap and the output cap (ring, log size equal to the bytes received); approvals (`covered`, `subject`, effects); `find_tools` finds the job tools. `tests/jobs_exit.rs` (Windows): the test binary runs itself as a process that starts a job whose shell starts a `ping`, then calls `std::process::exit`; the `ping` is gone after the exit (`KILL_ON_JOB_CLOSE`). The TUI takes `/kill` only as a word, so a user command `/killport` keeps its name (review). `tests/find_tools.rs` checks the job tools are deferred in the Claude body; `tests/tools_fs.rs` the builtin order.
