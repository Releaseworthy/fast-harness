# D75: the window renders at a fixed scale on the vsync renderer

Date: 2026-11-14. Branch `gui-dpi-stripes`.

## Owner report

1. Fast Harness must not follow the Windows display scale: at 50%, 100%, 300% or 500% it looks as at 100% (1 logical px = 1 physical px), also after a move to a monitor with another scale, and stays crisp.
2. Horizontal stripes that look like tearing (vsync off) when scrolling or resizing.
3. Gradients and the composer frame, buttons and icons look doubled, "ghosting".

## Observed (release build, 3840x2160 monitor at 200% (GetDpiForMonitor 192), second monitor 2048x1536 at 96)

- Scale: the window got scale factor 2.0 from winit (per-monitor DPI aware V2): `preferred-width/height` 1100x740 became a 2200x1480 client (`out/fh-window/before-start.png`). No code forced a factor; `SLINT_SCALE_FACTOR` was unset, so Slint took `winit_window.scale_factor()` (i-slint-backend-winit 1.18.1 `winitwindowadapter.rs` 602 to 669).
- Tearing: the software renderer presents through softbuffer 0.4.8 `backends/win32.rs`: one `BitBlt` per damage rectangle to the window DC with no sync to DWM composition and no vsync. Screen grabs during a `SetWindowPos` resize loop showed an unpainted band at the bottom right of a frame (`out/fh-window/before-resize/sheet.png`); the owner's stripes while scrolling were not caught on a grab.
- Ghosting: `Halo` drew two translucent rings (5px and 2px out) and `Elevation` three offset translucent fills (1, 3, 7 px): at 1:1 they show as doubled outlines and stepped arcs under the composer, the jump button and tool cards. The backdrop was a 135deg gradient between two near-equal dark colours: 8-bit steps showed as diagonal bands.

## Decision

- `src/display.rs` runs first in `main`: it sets `SLINT_SCALE_FACTOR` to `uiScale` (user layer, default 1.0, clamped 0.5 to 4) unless the variable is already set. Slint reads it when it creates the window and then ignores winit's `ScaleFactorChanged`; `window_events` answers that event by requesting the current physical size from winit's `InnerSizeWriter`, so a move to another monitor keeps the size. The process stays per-monitor DPI aware, so Windows never stretches a bitmap.
- Renderer: `renderer` (user layer) `auto` (default) is Slint's winit default: FemtoVG on OpenGL with swap interval 1 (`renderer/femtovg/glcontext.rs` 208, vsync), falling back to the software renderer when OpenGL fails (`lib.rs` `try_create_window_with_fallback_renderer`). `software` and `femtovg` force one; `SLINT_BACKEND` overrides both. Slint 1.18.1 has no vsync switch for the software renderer and no hook before its present (option b, DwmFlush, needs a fork of `renderer/sw.rs`).
- Visuals: one 3px glow ring for `Halo`, one real blurred drop shadow for `Elevation` (drawn by FemtoVG, absent in the software renderer, where cards are flat), a flat backdrop.

## Cost (measured with `out/fh-window/probe.ps1`, 30 s idle)

| | CPU idle | private memory |
|---|---|---|
| software (before, 2.0 scale) | 0 to 16 ms | 76 MB |
| femtovg (after, 1.0) | 16 ms (composer focused, caret rest at 5 s) | 260 to 277 MB |
| software (after, 1.0) | 0 ms | 67 MB |

The OpenGL driver costs about 200 MB: `"renderer": "software"` gives it back and brings the tearing back.

## Unverified

- Tearing gone under FemtoVG is inferred from vsync on the swap chain; screen grabs could not catch it before either. Owner check needed.
- Windows scale changes (50%, 300%, 500%) and a real move between the two monitors were not tried: the scale was not changed on this machine. The window reported 1100x740 on the 192 DPI monitor (scale 1.0).
