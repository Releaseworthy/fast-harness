# D59: One turn runner

Owner decision 2026-11-13, gate G7 option a (`docs/architecture-plan.md`): the front ends run their turns through `service::Service` in process. Chunk 25A moved the TUI and `serve`; chunk 25B moves the GUI.

## Contract

- **Thread.** `Service::start(session, Start, Sink, Done)` takes the conversation out of the session and runs the turn on `turn-<session id>`. The agent is built on that thread (`Host::agent`). No front end spawns a turn thread.
- **Guard.** A panic anywhere on the turn thread (the agent's build, the loop, the sink) is caught (`catch_unwind`): the turn ends `TurnOutcome::Failed`, the sink gets `AgentEvent::Error("the turn stopped on an internal error: <panic message>")` (skipped if the sink panics again), and the conversation is reopened from its log (the one in memory when the log does not read). `Finished::panicked` says so. The session is idle again, `done` runs exactly once (a panic in `done` is caught too), the session's mutexes recover from poison, and the on-disk lock (`session::lock::Held`, owned by the turn's inbox file) is dropped by the unwind.
- **Queue.** The session keeps the steers sent and not yet read (`Session::steer`, cleared by the turn's `UserInput { steer: true }` and at the end) and the follow-ups (`queue`, `remove_queued`, `drop_queue`, `take_next`). At the end of a turn the inbox's leftover goes first in the follow-ups, whatever the outcome; a front end starts the next one with `take_next` after `Done`. `serve` queues through the inbox (`Input::FollowUp`) and reports its leftover, so it drops the session's queue in its `done`.
- **Pause, stop, resume.** `pause` and `cancel` set `pausing` and `stopping` until the end; the end sets `unfinished` (`Paused`, `Cancelled`, else `Interrupted` when the history can resume); `can_resume` and `Start::Resume` continue it.
- **View.** `Session::status()` is one snapshot: running, stopping, pausing, steering, queued, unfinished. `Session::set_config` gives the next turn the front end's model and effort.

## What a front end keeps

Drawing, keys, its copy of the queue for the view (the TUI's `Ui::queued`, applied to the session at the key that edits it), its notes and status texts. The TUI's host (`tui/turns.rs` `TuiHost`) wraps `app::RuntimeHost` (shared with the TUI through `RuntimeHost::runtime()`): a build error names F2, and the build's notes reach the view before the turn's events. Its panic hook skips `turn-*` threads so a caught panic does not restore the terminal.

`-p` ran its turn with `Agent::run_turn` until 2026-11-13; see Closed later.

## Part B (GUI, 2026-11-13)

- The window has one `Service`; each session view (`gui/runs.rs` `Run`) holds its `Arc<Session>`, transcript, `turn_from` and a view-side `busy` flag (set at start, cleared when `Finished` reaches the UI thread). Steer, queue, chips, pause, Stop and Resume go through the `Session` API; the run table keeps only views (parked while busy or queued, a dropped idle view closes its session).
- The GUI runtime stays on the UI thread, so the agent is built there as before and handed to the turn thread by `gui/host.rs` `GuiHost` (`prepare` then `Host::agent` takes it by session id).
- C6: `Runs::apply(id, event)` applies an event to its own session's transcript and returns whether that session is shown; only then do the rows, the status and the panels (`Panels::session`) see it.
- A panicked turn: `Finished.panicked` shows the crash-log sentence; the guard's error event shows in the transcript; the panic hook still writes `crash.log` (thread `turn-<id>`).
- `app::words`: `state_word` with `Voice::Window` / `Voice::Terminal` (the two front ends word states differently on purpose), `Marks`, `tokens`, `duration`.
