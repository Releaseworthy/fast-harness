# D58: Tool progress and output parts

Owner, 2026-11-13 (docs/architecture-plan.md gate G9, option b, finding A4). `ToolCtx::progress(&self, text)` reports live text from the tool's thread or threads it starts; it goes to a private `Progress` (`dyn Fn(&str) + Sync`) set by `with_progress`, does nothing outside a session, never blocks or panics. The agent thread gets it over the batch's result channel (one channel, so order holds) and sends `AgentEvent::ToolProgress { id, chunk }` after the call's `ToolCall` and before its `ToolResult`. Live only: never traced, never in a message or request (efficiency-plan section 3); JSON `tool_progress` (`id`, `chunk`), ACP `tool_call_update` `in_progress` with content. `shell` sends its output as it arrives: at most one text per 100 ms, the newest 16 KB at most with `[N bytes of output skipped]` when more came, never splitting a UTF-8 character; its result is unchanged. Views: `view::Item::Tool.live` keeps the newest 8 lines (256 bytes each, escapes stripped, `\r` restarts a line) under the running tool in the TUI and the GUI; the result drops it, so live equals replay. `ToolOutput` fields are private: `#[non_exhaustive] enum Part { Text(String) }` held as a list, read by `text()` (text parts joined), `into_text()`, `parts()`, `is_error()`, `bytes()`, `spilled()`, built by `ok`, `err`, `new`, `from_parts`. Enum variant fields are fixed: new data is a new variant.
