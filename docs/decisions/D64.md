# D64: Approvals

Owner decision, 2026-11-13, gate G11 option b of `docs/architecture-plan.md` ("G11 b (default `off`), after G7"). Part A: core, service, `serve` and `-p`. The TUI and GUI prompts are part B.

## Settings
- `approvals` in `config.json`: `"off"` (the default: the gate costs one comparison per call) or `"ask"`.
- `allow`: `{"commands": [...], "paths": [...], "tools": [...]}`. `commands` are command prefixes of the `shell` tool, `paths` are folder or file prefixes of `write` and `edit` (absolute, or relative to the session's working folder), `tools` are tool names allowed whatever their arguments (an MCP or plugin tool).
- Layers: the user layer sets both. A trusted project may set `approvals` to `"ask"` and nothing else, and its `allow` is dropped (`config/layers.rs` `project_rule`): a project must not weaken the user's gate, and an allow entry is a weakening. An untrusted project changes nothing (D62). `fast-harness config` and `doctor` show the value and its layer as for every key.

## The gate
- Where: `agent/approval.rs`, called by the tool runner (`agent/tool_run.rs`) after the PreToolUse hooks (`agent/hooks.rs`) and before the run, so it sees the final arguments; a hook that blocks a call means no question.
- What asks: with `ask`, a call whose effect is `Write` or `Run` and that the allow list and the session's grants do not cover. `Read` calls (`read`, `grep`, `glob`, `find_tools`) never ask. An unknown tool asks. The subagent tools (`subagent`, `agent_send`, `agent_stop`, `agent_output`) do not ask: they run nothing themselves, and each child's calls ask.
- The request is the live event `AgentEvent::ApprovalRequest(ApprovalRequest { id, call_id, tool, effect, summary, arguments, agent })`, then `AgentEvent::ApprovalDone { id, answer }` with `once`, `session`, `declined`, `cancelled`, `paused` or `refused`. `summary` is one line: `run: <command>` or `write file: <path>` (the view's tool detail is a higher layer, so the config layer builds it).
- Answers (`agent::Answer`): `Once`; `Session`, which covers later calls of the same tool with the same command (whitespace collapsed, the whole text: the narrowest prefix), the same normalised path (`write`, `edit`), or the same arguments (other tools), until the session closes; `No(reason)`, which gives the model `not run: the user declined this call: <reason>` and the turn goes on. An answer never writes the settings file.

## Matching fails closed (`config/approvals.rs`)
- A command is covered only when it is one simple command whose first words equal the words of an allowed prefix (ASCII case ignored, as pwsh resolves commands). Compound, so it asks: `;`, `&` (also `&&` and the call operator), `|` (also `||`), `(` and `)` (also `$(` and `@(`), `{` and `}`, `<` and `>` (every redirection), the backtick (escape and line continuation), a line break, and any character outside printable ASCII (pwsh reads some Unicode dashes and quotes as operators).
- A path is joined to the working folder, `.` and `..` resolved by name (a `..` above the root asks), the longest existing ancestor resolved through links and junctions (`canonicalize`), and lower-cased on Windows; it is covered when it starts with an allowed prefix normalised the same way, component by component. Another drive or a name that only starts alike (`srcx`) asks.

## The wait
- The tool thread blocks on a condition variable (`Gate`, one per service session, shared with its subagents). It ends on the answer; on Stop (`Session::cancel`: the call answers `cancelled before it ran`, as a cancelled call does today, and every later request of the turn too); on pause (`Session::pause` or `Input::Pause`: the call answers `not run: the turn was paused ...` and the turn ends `Paused`); on close (`Service::close` cancels). A 500 ms timed wait is the only backstop, for a child stopped by `agent_stop` through its own flag. No timeout: a person may be away.
- The agent thread keeps forwarding events and sees a cancel while a call waits. A steer typed during a wait keeps D39: it waits in the inbox, does not answer the request, and joins the history after the step's results.
- Subagents ask through the gate of their session; `agent` is `label (session id)`. `Session::status().waiting` lists the pending requests of the turn and of background children, so a front end can mark a session that waits.

## Front ends
- `Session::approvals()`, `Session::answer(id, Answer) -> bool` (false: unknown or answered), `Session::set_answering(bool)`. A session nobody answers for (the default) refuses at once: the model gets `not run: approvals are on ... and nobody can answer in this session ...` and the events show `refused`. The TUI and GUI stay there until part B.
- `-p` has no gate: every call `ask` would ask is refused with that text, stderr says once how to allow it (`allow` or `"approvals": "off"`), `-p --json` prints `approval_request` and `approval_done`.
- `serve` sessions answer: each request goes out as ACP `session/request_permission` (id `fh-approval/<session>/<request id>`, options `allow-once` (allow_once), `allow-session` (allow_always, scope in its name), `reject-once`), checked against <https://agentclientprotocol.com/protocol/v2/tool-calls.md#requesting-permission> on 2026-11-13. A `cancelled` or unknown outcome declines (the schema says never to treat it as approval). `_fh/approve {sessionId, requestId, answer: once|session|no, reason?}` answers too; an unknown or answered id is `-32602`.

## The log
No new trace record. A declined, refused, cancelled or paused call is in its traced tool result, so a replayed transcript equals the live one; the request events are live only (as `ToolProgress`, D58) and the views ignore them. Left: who allowed an allowed call is not in the log; a `tool/approval` record (a trace version bump) can come with part B if the owner wants it.

## What approvals do not protect against
A `Read` tool (it may read secrets), a hook command, an MCP server process and what it does on its own, a plugin's native code, a command tool file's own program under an allowed name, and a command an allowed prefix can be made to abuse (`git` with `-c core.pager=...`, `cargo` running a build script). Allow narrow prefixes.
