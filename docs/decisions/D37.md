# D37: Output diet

Owner, 2026-11-12 (docs/efficiency-plan.md phase 12): tool results shrink once, before the first send, never after. One byte budget per result: `toolOutputBytes` (default 8192) or the tool's `toolOutput` entry (`{"read": 16384}`), at least 1024, looked up only in `Config::tool_budget` (phase 17A adds tool files there). A longer result keeps a cut and ends with `[full output: <path>, <bytes> bytes, <lines> lines; read it with offset and limit or grep it]`, the whole text in `<session>.out/<callId>.txt` (no session: `[output cut: ...]` and no file). Cuts: the head on a line boundary; shell a quarter head (2 KB of 8 KB) and the rest tail with `[... n bytes cut ...]` between (errors are at the end); subagent the answer plus its stats line. `read` returns whole lines from `offset` up to the budget, then `[lines a to b of n; continue with offset b+1]` (no head-and-tail cut); a range a call of this session already returned (same path, offset, limit, size and modified time) answers `[unchanged since call <id>]`. That state lives in `Conversation::tool_session` and starts empty on resume (a resumed session re-reads once); compaction (phase 13) must clear it. `grep` shows 50 matches (`max_results`) grouped by file (a path line, then `  N: text`) and `[n more matches in m files; ...]`; `glob` 100 paths; `find_tools` 5 tools unless the call passes `limit` (at most 20). Trace version 6: `tool/result` has `bytes` and `spilled`; `stats` counts spilled results with the clipped ones; `view::tool_detail` shows a `full output` field. Acceptance (`tests/output_diet.rs`): a scripted 60-step session with ten 40 KB results sends 95,267 request bytes at step 60 against 343,727 with the old 32 KB clip (-72%), and no logged result exceeds its budget.
