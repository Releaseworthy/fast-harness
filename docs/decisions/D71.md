# D71: The Claude Code version follows the releases

Owner, 2026-11-14: Claude OAuth calls failed with `BadRequest (HTTP 400): invalid_request_error: Claude Code 2.1.280 does not support this model; version 2.1.290 or newer is required.` The version in `user-agent: claude-cli/<version>` was the constant `2.1.280`. He asked for the fix and for the version to update by itself each time Fast Harness opens, without a restart.

Source (2026-11-14): `https://registry.npmjs.org/@anthropic-ai/claude-code/latest` answered `"version": "2.1.323"` (dist-tags: latest 2.1.323, stable 2.1.311, next 2.1.324).

- `llm::anthropic::claude_code` holds one version per process, read by every request (`wire::headers`). It only moves forward: `offer` takes a plain `major.minor.patch` newer than the current one (anything else is refused, so a registry answer cannot inject a header).
- Start: `BUILTIN` (2.1.323), then `~/.fast-harness/claude-code.json` (`{version, fetchedAt}`, written through `store::write_atomic`, a cache: last writer wins).
- Open: the CLI commands (`auth_choice::runtime`) and the GUI call `Runtime::update_claude_code`, a background thread once per process that reads the npm `latest` tag (20 s limit), offers it and writes the cache. Requests sent after it use the new version: no reload. A failed fetch is silent and keeps the current version (the TUI owns the terminal).
- Self-heal: an OAuth HTTP 400 whose message says `version X or newer is required` offers X; when that raised the version the same call goes once more (`anthropic::stream`). The refusal comes before any delta, so nothing reached the view twice. API key calls are not touched.
- `claudeCodeVersion` (user layer, read at start): `auto` (default) follows the above; a release such as `"2.1.323"` pins it, and then neither the fetch nor the 400 moves it.
- Tests: `tests/claude_code_version.rs` (its own process, steps in order), pure parsing in `claude_code_tests.rs`.
