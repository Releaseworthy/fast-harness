# D60: Session index

Owner decision 2026-11-13, gate G10 option a (`docs/architecture-plan.md`): `sessions/<slug>/index.json` caches the summary of each log; `latest` picks the highest id from the file names; a resume parses its log once; a damaged line that is not the last is skipped with a note. Chunk 26A is the core and the CLI; chunk 26B moves the lists of the TUI and the GUI to a worker thread.

## The index

- **File.** `~/.fast-harness/sessions/<cwd slug>/index.json`, version 1: `{"version":1,"logs":{"<id>.jsonl":{"size","modified","summary"}}}`; `modified` is nanoseconds since 1970, `summary` is `{id, createdAt, title, turns, lastTime, unfinished?}` or null for a log that does not read. Format text: `docs/formats.md` "Files on disk". The trace format does not change.
- **Staleness.** `session::list` stats every `*.jsonl` (not `*.inbox.jsonl`) with `fs::metadata` (on Windows it asks the open file, so a log being written is current; a directory entry can lag). An entry whose size and modified time both match is used without reading the log; anything else is one full parse of that log. The stat is taken before the read, so a log that grows meanwhile is stale on the next list, never cached as current. Entries of logs that are gone are dropped. A log replaced with the same size within the same modified-time tick is not seen (accepted).
- **Who writes.** Only a list, and only when an entry changed, through `store::update` (lock `index.json.lock`, wait 500 ms, temp file and rename): inside the lock it keeps the entries another process wrote for logs this list did not see that still exist. Two processes listing at once leave a whole file; the loser's view costs at most a parse on the next list. `latest` and the session writers do not write the index.
- **A running session.** Its log grows at every event, so its entry is stale at the next list: one parse of that one log (about 2.5 ms per MB measured, `docs/perf.md` phase 26A). The turn end does not update the index (no coupling of the writer to the cache).
- **Damage.** A missing, damaged or other-version index is rebuilt (every log parsed once, then written). An unwritable index or folder: the list answers from the logs and does not write; never an error, never a wrong answer.
- **API for a worker thread.** `session::list(home, cwd)` and `session::list_counted` (`Listing { sessions, parsed, cached, written }`) are plain functions with no shared state but the file: call them on any thread.

## `latest`

The highest file name of the form `yyyymmdd-hhmmss-xxxx.jsonl` (`session::new_id`: the UTC second, then a 4-hex counter), answered from the index entry when its stamp matches, else by parsing that one log; a log that does not read falls to the next name. Names sort as time to the second. Within one second, one process's ids rise with its counter; ids of two processes in the same second order by their counters, whose start differs per process, so the pick between them is arbitrary (the old list ordered by `createdAt` in ms). Foreign names (`zzz.jsonl`) are skipped; a folder with no id-named log falls back to `list`.

## One-pass resume

`Conversation::reopen(home, cwd, id) -> (Conversation, Vec<TraceEvent>)` reads the log once through `TraceWriter::open_parsed` (one open handle: the bytes, the parse, the append position, then the torn-line cut); the history (`session::replay_events`), the turn, the last `request/header`, the context numbers, the unfinished state and the depth come from those events, and the replay is checked before anything is written. `Conversation::resume` is `reopen` without the events. 26B: `gui/app.rs` `open_session` can take the events from `reopen` for `Transcript::from_trace` instead of `trace::read` (the fourth parse). `Conversation::next_seq()` exposes the append position.

## A damaged line

`trace::reader::parse` skips a line before the last that is not a valid event and lists it in `Parsed::skipped` (1-based line, byte offset); `Parsed::note()` is one note naming the first (and how many more). A damaged last line keeps its handling (a torn write, cut on append); a bad header still fails. The log is never rewritten for a damaged middle line. The note travels in the reopened `Conversation` (`take_notes`, handed out once) and `Runtime::agent_with` adds it to the notes of the first agent built, so the TUI, the GUI, `-p` and `serve` show it with the first turn; `fast-harness trace <id>` prints it on stderr. `repair` closes a tool call whose result was on the damaged line.
