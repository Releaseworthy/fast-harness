# D83: Context diet without breaking the cache

Owner, 2026-11-14: a subagent of his (claude-fable-5-2, 1M window, effort high, log `20261113-195342-6143.jsonl`) reached 350,608 context tokens in 47 calls; Fast Harness must spend as few tokens as possible in every session, and (same day, change of direction) nothing may lose the prompt cache: no pruning or rewriting of content already sent.

## Measured first (owner's logs, `out/fh-ctx/cache.ts`, `reads.ts`)

- The cache already works on every step: child 47 calls, cache read 10,221,171, cache write 344,495, uncached input 96, output 60,375 tokens: 96.7 % hit; each step reads the whole previous context and writes only what it added. Parent (`20261113-195004-6140.jsonl`): 12 calls, 80.0 % hit (few steps, so the writes weigh more).
- Cost in base-input units (read 0.1, write 1.25): child 1.45 M, of which cache reads are 70 %. Cost is steps times context, so the lever is what enters the context, not the hit rate.
- What entered: 165 results, 687 KB; `read` 124 calls, 601 KB (75 without `offset`/`limit`, 51 cut at the 8 KB budget, no exact repeat: the 23 re-reads of a path were other ranges); `grep` 37 calls, 69 KB; `shell` 3, 17 KB. Line-number prefixes are 64 KB (10.6 %) of the read bytes. Thinking: 40 blocks, 54 KB of summary text plus 195 KB of signatures; about 100 K of the 350 K tokens are not tool results, which fits the full thinking of the turn being billed as input.

## Sources (fetched 2026-11-14)

- [Preserved thinking](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking) (claude-fable-5-2 is listed): a thinking block is tied to `system`, `tools` and every earlier message; if any changes the block fails the prefix check and the request can get a 400, "so only add to a conversation".
- [Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing) (beta `context-management-2025-06-27`): server-side `clear_tool_uses_20250919` never invalidates thinking but "invalidates cached prompt prefixes when content is cleared" (hence `clear_at_least`); `clear_thinking_20251015` keeps at least the turn in progress (`keep` N > 0 counts it, and a user message holding only `tool_result` blocks continues that turn), and clearing invalidates the cache where it happens. Fable and Mythos keep all prior thinking by default.
- [Thinking in tool and multi-turn workflows](https://platform.claude.com/docs/en/build-with-claude/thinking-tool-workflows): pass thinking blocks back complete and unmodified with the tool results.

## Decision

1. No pruning of old tool results, client or server side: the client edit fails the prefix check of every later thinking block, and server clearing rewrites the cached prefix at each clear. Not implemented.
2. Thinking stays as it is: inside a tool loop the docs give no way to drop it (the turn in progress is always kept), and dropping earlier turns' thinking costs a cache rewrite at each new turn.
3. Shrink what enters, never what was sent (`config/context.rs`, `context` in `config.json`):
   - `context.readHeadBytes` (default 4096): a `read` without `offset` and `limit` returns whole lines up to 4 KB, then `[lines 1 to b of n; continue with offset b+1; first grep it, then read the lines you need with offset and limit]`. A file under 4 KB comes whole. Why 4 KB: today's head is the 8 KB budget (~2.5 K tokens, ~175 lines at the log's 46 bytes per line); 51 of 124 reads paid it in full. A byte entering at step s of 48 costs 1.25 + 0.1 x (48 - s), on average 3.65 units per token, so 4 KB saved at mid-turn is ~4.6 K units, while one extra step at the child's mean context (~175 K) costs ~17.5 K units: the head pays off while fewer than about one head read in four needs a follow-up step of its own. 0 restores the old head.
   - `context.dedupeReads` (default true): lines inside a range an earlier read of this session returned (same canonical path, size and modified time) answer `[unchanged since call <id>]`; before, only the identical request did. A cut result counts up to its last line. The ranges are forgotten at a compaction (D38) and on reopen, so the earlier result is always still in context.
   - One line in the built-in system prompt (subagents use the parent's frozen prompt, so it reaches them too): "Find code with grep or glob, then read only the line ranges you need." The `read` description says the same. Both are frozen per session: open sessions keep theirs.
4. Kept as is: grep already groups matches under one path line; the `N: ` line prefix stays (edit and ranges depend on it; 10 % of read bytes).

## For the owner: cache-breaking options not implemented

- Compaction threshold: today 50 % of the window, capped at 500 K (D38); the child at 350 K never compacted. A what-if on its per-step growth (`out/fh-ctx/compact-sim.ts`: summary call of 3 K output tokens, 6 K summary) gives 1.47 M units as run, 0.93 M with compaction at 200 K (1 compaction, -36 %), 0.82 M at 150 K (2, -44 %), 0.77 M at 100 K (3, -47 %). Each compaction rewrites the prefix once and drops the turn's thinking and detail, so the choice is his (`compaction.maxTokens` already sets it).
- Server-side `clear_tool_uses_20250919` with `clear_at_least`: the same kind of saving in batches, one cache rewrite per batch, thinking kept; needs the beta header on the OAuth path and a live check.
- Lower subagent effort: the ~100 K tokens of thinking in the child scale with effort.
