# D88 Session file state survives a reopen; main-session cache TTL by step

- File state: `<id>.files.json` beside `<id>.out` (version 1, `{"version":1,"files":[{path,hash,call}]}`) is written through `store::write_atomic` on every read/edit/write record and loaded by `ToolSession::new`, so `-c` and a reopened GUI session (both `Conversation::reopen`) keep what was read and written. Line hashes and read ranges are not kept: a restored entry has no `base` (D87), so the first read after a reopen returns the file whole, also after an edit made since the reopen. A file changed on disk since has another hash and is still refused. The hash is `DefaultHasher` (fixed keys): a toolchain change only makes edit ask for a read again.
- API rule (platform.claude.com/docs/en/build-with-claude/prompt-caching, "Mixing different TTLs", read 2026-11-15): a hit on a 5 minute entry does not count when a 1 hour `cache_control` block after it misses; billing is A = last hit, B = last 1 hour breakpoint after A (A..B written at 1 hour), C = last breakpoint (B..C at 5 minutes). Live (2026-11-15) the first D88 (1 hour tail on every turn start, 1 hour anchor on the latest turn's user message) read 1,118 and wrote 1,607 tokens at 1 hour on a turn started one minute after the last loop step: the loop it had cached for 5 minutes was written again at 1 hour (1.25x + 2x per loop token on every turn but the last).
- Cache TTL now (`cacheTtl: auto` in the TUI, GUI and `serve`, `interactive`; `agent/cache_clock.rs`, `llm/anthropic/cache.rs`): tools and system 1 hour; the message tail 5 minutes, except a turn start (trailing user message) whose previous answered request started 4 minutes ago or more, or is unknown, which gets 1 hour; a 1 hour anchor sits only on the user message where the last 1 hour tail was written (named by the number of assistant messages before it), so it is a hit, never a miss after 5 minute hits. After a reopen the start of the last request comes from the log's last `request/context`; the anchor is unknown after a reopen or a compaction until the next 1 hour tail. Order stays 1 hour before 5 minutes; a 5th breakpoint drops the OAuth identity block's, then the last tool's. Explicit `cacheTtl: "1h"` keeps every breakpoint 1 hour, `"5m"` every one 5 minutes; subagents unchanged (system 1 hour, messages 5 minutes).
- Measured (2026-11-15) on the owner's 15 main sessions in `~/.fast-harness/sessions` (19 turn starts after an earlier request; gap from the previous request's start: 11 under 1 minute, 6 at 1-4, 0 at 4-60, 2 over 60 minutes), replaying their recorded token counts (read 0.05x, 5 minute write 1.25x, 1 hour write 2x, lifetimes from request start and refreshed by a read, 20-block lookback at 2 blocks per step): all 1 hour 0.76 M base-token units, the first D88 0.75 M, idle-aware 0.61 M (chosen, 20% below all 1 hour).
