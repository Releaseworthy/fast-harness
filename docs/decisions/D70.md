# D70: Image input (core)

Owner, 2026-11-13: phase 31 "image input" (finding A4). This is the core; attaching and thumbnails in the TUI and the GUI are a second chunk.

Sources (2026-11-13): platform.claude.com/docs/en/build-with-claude/vision (base64 `image` blocks, png/jpeg/gif/webp, 8000 px edge, above 20 images a stricter edge (3000 px stated, 2000 used here), 10 MB base64 per image on the Claude API and 5 MB on Bedrock and Google, 100 images per request on 200k models, tokens = ceil(w/28) x ceil(h/28) with a 2576 px / 4784 token high-resolution tier and 1568 px / 1568 standard, images inside `tool_result` content, vision on every model); developers.openai.com chat completions reference (`image_url` part `{url, detail}` with a data URL, a `role: tool` message takes text parts only).

- Contract: `types::ImageRef { path, media_type, bytes, width, height }` (`#[non_exhaustive]`, `ImageRef::new`), `Block::Image(ImageRef)` and `tools::Part::Image(ImageRef)` (new variants, D57/D58: no variant changed), `ToolOutput::image(text, image)` and `images()`, `Message::images()`; `ImageRef` is re-exported from `ext::v1`.
- Storage: `media::attach_bytes(dir, bytes, type)` / `attach_file(dir, path)` check and keep the image once as `<session>.media/<first 32 hex of sha256>.<ext>` (`store::write_atomic`), beside `.out` and `.undo` (`ToolSession::media_dir`). The trace holds only the reference. `crypto` (base64, SHA-256) moved from `accounts` to the crate root (re-exported as `accounts::crypto`) so `media` can use it.
- Caps (`media`): png, jpeg, gif, webp by their bytes (a declared type must match); at most 3,750,000 bytes (5 MB base64, the smallest platform limit); longest edge 8000 px; the size comes from the headers read by hand (`media::sniff`). No downscale: the workspace has no image decoder and none was added; an image over a cap is refused with words, and the provider downscales one over its long edge. Downscaling on the client stays open for the owner (it needs an image crate).
- Cost in words: `media::label` = `png 640x480, 12.3 KB, about 414 tokens`; a user message is `[image N: <label>]` + the image for each attached image, then the text (`media::user_message`, `user_text` for a live transcript: the same as a replay); `read` answers `<path>: image, <label>`.
- `read`: a file whose bytes are png/jpeg/gif/webp returns the line and `Part::Image`; a broken or over-cap image is an error result with the reason; without a session folder it is refused.
- Requests: `llm::images::prepare` runs once per body: images go when the model takes them, newest 100 only, above 20 only those within 2000 px; the bytes are read then. Any other image becomes `[image not sent: <why>; <label>]` (appended to its tool result in a tool message): a model without images, a missing or changed file (a reopened session whose media is gone), the count limits. Never an HTTP 400 from our side. Anthropic: `image` blocks with a base64 source, a tool image inside its `tool_result` content (text then image); the cache breakpoint may sit on an image block. openai-chat: `image_url` data URLs in user content; a tool image follows the tool messages as a user message `[image of tool result <id>]` + the image; a model takes images only with `"images": true` in its provider file entry (`ModelFile.images`, default false, so a custom model gets the placeholder).
- Prefix: the choice depends only on the history, the files and the model, so a rebuilt request is the same body; crossing 20 or 100 images changes earlier messages once (one cache miss).
- Tokens: `media::tokens` (the high-resolution tier, the costliest) is added to the compaction estimate.
- Trace version 13 (`docs/formats.md`).
- Front-end API (chunk 2): `Session::attach_image_file(path)`, `attach_image_bytes(bytes, type)`, `attached_images()`, `clear_attached_images()`; the next prompt carries the queue (`ToolSession::attach`, `take_attached`); refused while a turn runs (`Busy`). Show `media::user_text(text, images)` as the user item.
- Tests: `media/tests.rs`, `media/sniff_tests.rs`, `tools/output.rs`, `tests/images.rs` (Claude user image and trace without bytes, `read` image in its `tool_result` and a broken png, openai-chat data URL and placeholder, missing media after reopen, a version 12 log).

## Views

Chunk 2 (2026-11-13): the core item, the TUI and the GUI.

- **Core.** `view::Item::User` has `images: Vec<ImageRef>` beside `text`; `Transcript::push_user_images(text, images)` stores `media::user_text(text, &images)`, and the replay takes `Message::images()` of the trace's user message, so a live item equals the replayed one (test `an_attached_image_is_listed_then_sent_with_the_next_prompt`). `app::image_args` parses `/image <path>` and `/image clear` (never sent to the model; listed in `/help`). `platform::pick_file(owner, title)` is the existing IFileOpenDialog of the folder picker with `FOS_FILEMUSTEXIST` instead of `FOS_PICKFOLDERS` (the GUI attach button).
- **TUI (`tui/images.rs`).** `/image <path>` (quotes from Explorer's "Copy as path" removed, relative to the session folder) calls `Session::attach_image_file`; a refusal is an error note `image not attached: <words>`, during a turn `... a turn is running; attach it after the turn ends`. `/image clear` drops the queue. One line above the input while images wait: `images  <mark> 1 png 3x2, 88 bytes, about 1 tokens  (/image clear removes them)`, the mark `image` of the icon set (cod-file_media U+EAEA, verified in vscode-codicons `mapping.json`; plain `▣`, both one cell wide) in the accent role, the label in words. A terminal has no clipboard image: a pasted path is the way.
- **GUI (`images_view.rs`, `thumbs.rs`, `ui/attach.slint`).** Three ways in, all calling `Session::attach_image_file` on the shown session (opened in the service first, as a first message does): the composer's attach button (`Icons.file`, "Attach an image") opens `platform::pick_file` on a thread; files dropped on the window come through `slint::winit_030::WinitWindowAccessor::on_winit_window_event` (`WindowEvent::DroppedFile`, slint feature `unstable-winit-030`: it enables `i-slint-backend-winit`, already in Cargo.lock, no new crate; winit's Windows `drag_and_drop` defaults to true); `/image <path>` and `/image clear` typed in the composer (taken in `turn::send` before a steer, never sent). A refusal is the error banner `Image not attached: <words>`, during a turn `... a turn is running ...`. `AttachRow` sits between the queue chips and the jobs strip, one line per image: thumbnail, `image N` in the accent role, the label in words, an x (`remove-image(index)`: the core has no single removal, so the others are attached again from their media files). No clipboard image (Slint's clipboard API is text only; arboard sits inside the backend) and no click-to-open (no open-file helper: `open_url` takes http(s) only, `open_folder` folders only).
- **Thumbnails.** Slint's `Image::load_from_path` keeps the whole decoded image and a 5 MB LRU per thread (`i-slint-core` `graphics/image/cache.rs`), so the window never shows a file: `thumbs::get(path)` returns the cached small image or queues the path; one worker (`fast-harness-thumbs`, no timer) decodes the queue with `load_from_path` + `to_rgba8`, box-filters each to at most 128 px on its longest side and posts the pixels; the UI thread makes `Image::from_rgba8` and keeps the newest 64 by media path (the sha256 name), at most 64 KB each. The full image lives only on the worker, whose thread-local cache ends with it. The user row (`MsgRow.images: [ImageChip]`) draws 64 px thumbnails above its text, whose label lines are the text alternative (also each thumbnail's `accessible-label`); a file that fails to decode keeps a file mark. Rows hold their small images while the session is shown (the ListView recycles only the delegates, not the model).
- New `MainWindow` items `attached: [ImageChip]`, `attach-image()`, `remove-image(int)` (`docs/ui-contract.md`); the queue chips moved into `QueueRow` (`ui/queue.slint`) to keep `main.slint` under 500 lines.
- **Tests.** GUI `images_view_tests.rs` (a path becomes a chip with its label, the x removes one, a text file refused in words, `/image` typed never sent, a 300x200 png becomes a 128x85 thumbnail cached by its path) and `images_turn_tests.rs` (the attached image is in the Claude body, the user row has its chip and label lines, the live item equals the replay). TUI `images_tests.rs`: the image is listed, the next prompt's Claude body carries the `image` block, the line goes away, the user item equals `media::user_text` and the replay; `/image clear`, a text file refused in words, a missing file, `/imagex` not taken.
