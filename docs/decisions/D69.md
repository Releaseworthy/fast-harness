# D69: Undo of a turn's file changes

Owner, 2026-11-13: phase 31 "undo of a turn's file changes". This is the core part plus the command entry points; the TUI and GUI views are a second chunk.

## What is tracked

- Only `write` and `edit`. Both call `tools::undo::tracked_replace` instead of `atomic::replace`: before the first change of a file in a turn the session's `UndoLog` keeps its prior state (the bytes, or "did not exist"), and after each change the hash of what the turn left (FNV-1a 64 plus the length: it only has to see that a file changed since, not resist a crafted collision).
- Not tracked: `shell`, background jobs (D68), extension and MCP tools, and subagents (a child conversation has its own `ToolSession`, so its own store under its own session id). Every undo result ends with `UNTRACKED`: "Files changed through shell commands, background jobs or subagents are not tracked and were not undone."
- A tool call outside a turn (turn 0) or without a session tracks nothing.

## Storage

- `<session>.undo/turn-<n>/manifest.json` (format 1: `turn`, `files` [`path`, `existed`, `before` blob name, `after` hash], `bytes`, `notUndoable`, `undone`, `noted`) and one `<i>.bin` per file that existed, all written with `store::write_atomic`. The folder sits beside the log and the `.out` spill folder (`ToolSession::new` derives it from `out_dir`).
- `UndoLog` lives in `ToolSession` behind an `Arc`, shared with `service::Session` like the jobs (D68); `service/turn.rs` `reopen` hands it to a conversation rebuilt after a panic (`share_undo`). It reads the manifests on first use, so a reopened session knows which turns were undone.
- `agent/turn.rs` calls `begin_turn(conv.turn)` at the start of every turn, a resume included.

## Caps

- `TURN_CAP` 16 MiB of prior bytes per turn and `SESSION_CAP` 64 MiB per session (kept bytes of turns not undone). A file that would pass either marks the turn not undoable with the reason in words ("its earlier file content passed the 16 MiB cap per turn", "the session's kept file content passed its 64 MiB cap"); its blobs go at once, the files are still listed so a view can show the count. A blob that cannot be written or a prior file that cannot be read does the same. `UndoLog::set_caps` changes them (tests).
- An undo deletes the turn's blobs (the manifest stays, marked `undone`), so undone turns free their room.

## Undo

- `UndoLog::undo_last(force)` takes the newest turn with tracked files that is not undone. Not undoable: refused with the reason. Otherwise every file's current hash is compared with what the turn left; any difference (the user, a later `shell` command or job changed it, or removed it) is a conflict, and without `force` the undo is refused listing the conflicting files: nothing changes. All kept blobs are read before the first write, so a missing blob also changes nothing. Then each file gets its prior bytes back (`atomic::replace`, parent folders recreated) or, if the turn created it, is removed; folders the turn created stay. A write that fails mid-way is listed in `errors` and the rest continue (the files were checked a moment before).
- A second undo takes the turn before: undo goes back turn by turn, each with the same conflict check.
- `UndoOutcome { turn, restored, removed, conflicts, refused, errors, forced, untracked }`, `text()` for a transcript line.

## Where it is called

- `service::undo::undo_conv(&mut Conversation, force)` runs it and, when files changed, writes the trace record. `Session::undo_last_turn(force) -> Result<UndoOutcome, ServiceError>` holds the session state lock and returns `ServiceError::Busy` while a turn runs (its thread holds the conversation), so undo is refused during a turn. `Session::undo_info() -> Option<UndoInfo { turn, files, not_undoable }>` is the query for a view (no lock on the conversation, works while a turn runs).
- `/undo [force]`: `service::undo::command(text) -> Option<bool>`, re-exported as `app::undo_args`, and listed in `/help` (`BUILT_IN`, so a `commands/undo.md` cannot take the name). `serve`: a `session/prompt` or `_fh/steer` text `/undo [force]` is answered locally (the `/help` path) and never reaches the model or the follow-up queue; `_fh/undo {sessionId, force}` and `_fh/undo_info {sessionId}` are the JSON methods (`docs/service.md`). The TUI and the GUI call `undo_last_turn` in the second chunk; until then `/undo` typed there is sent as text.

## The model's view (frozen prefix)

- Nothing earlier is touched (docs/efficiency-plan.md: append-only). After an undo the manifest has `undone: true, noted: false`; the next turn's user message takes `UndoLog::take_note()` and starts with one text block `[undo] The user undid the file changes made with write and edit in turn N. Restored to their content before that turn: ... Removed (that turn created them): ... Read a file again before editing it.`, after the context update (D36) when both exist. A resumed turn adds it as user text like the context update. `noted` is saved, so the note goes exactly once and survives a reopen between the undo and the next turn.

## Trace (version 12)

- `undo` `{turn, restored, removed, forced}` (`trace::record::Undo`, D61), written only when files changed (a refused undo logs nothing). `view/replay.rs` shows it as an info note `undid the file changes of turn N: restored ...; removed ...`. `docs/formats.md` has the version line.

## Tests

`tests/undo_turns.rs`: write then edit then undo restores the exact bytes (CRLF kept); a created file is removed; a conflict changes nothing, lists the file and logs nothing, and force overwrites; a 4-byte turn cap marks the turn not undoable and the undo refuses; undo during a running service turn is `Busy`, `/undo` parsing; the note reaches the next request body while earlier messages, system and tools are unchanged; after reopen the replay shows the undo, the store knows turn 2 was undone, a second undo takes turn 1 and a third finds nothing.
